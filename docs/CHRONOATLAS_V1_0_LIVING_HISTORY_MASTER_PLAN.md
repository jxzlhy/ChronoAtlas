# 一、最高目标

你现在正式接管 ChronoAtlas 项目。

你不再只是一个按照用户要求编写代码的程序员，而是这个产品的：

- 产品负责人
- 创意总监
- 3D 图形工程师
- 前端架构师
- UI/UX 设计师
- 历史数据研究员
- 交互设计师
- 性能优化工程师
- 测试工程师
- 质量审查负责人

你的最终任务不是简单地给现有项目增加几个功能，而是将 ChronoAtlas 从一个具有 3D 地球、历史事件、人物和因果关系的探索 Demo，逐步升级为真正具有产品完整度、视觉辨识度、知识深度和持续探索价值的交互式世界历史平台。

## 产品愿景

**站在太空看历史，让世界历史在一颗可以交互的地球上真正活起来。**

用户可以通过一颗 3D 地球：

1. 探索某个年份的世界。
2. 观察不同地区正在发生的历史事件。
3. 理解不同事件之间的历史联系。
4. 追踪重要人物的一生及其历史影响。
5. 观察战争、航海、探索、贸易和文明发展的地理轨迹。
6. 理解国家、帝国、殖民地和疆域如何随时间演变。
7. 从一个事件不断探索到另一个事件，形成连续的历史知识体验。

ChronoAtlas 不应该只是一个可以旋转的地球，也不应该只是一个把历史事件放在地图上的网站。

它应该是一个：

**以时间为轴、以地球为空间、以事件为节点、以人物为线索、以历史关系为网络的交互式世界历史系统。**

# 四、第一阶段：Historical Intelligence
# 历史数据基础设施升级

优先级：P0

这是整个 V1.0 的基础。

在大量增加历史事件之前，先让历史数据具备可追溯性、可维护性和可扩展性。

## 4.1 升级历史事件数据模型

检查现有 HistoryEvent 类型，在兼容现有数据的前提下，设计更完整的历史事件模型。

建议考虑：

- 唯一 ID
- 中英文标题
- 开始时间
- 结束时间
- 时间精度
- 经纬度
- 地理位置
- 地理精度
- 所属国家或地区
- 所属大洲
- 事件分类
- 重要程度
- 中英文描述
- 事件背景
- 历史影响
- 参考资料
- 相关人物
- 相关事件
- 标签
- 数据审核状态

时间精度需要区分：

- 年
- 月
- 日
- 时间段
- 约略年代

地理精度需要区分：

- 城市
- 地区
- 国家
- 全球
- 多地点

不要为了让数据结构看起来完整，就强迫所有事件填写不存在的信息。

对于缺少准确日期、地点或来源的历史事件，应明确标记，而不是编造精确数据。

## 4.2 建立历史资料来源体系

每条重要历史事件尽可能提供可追溯的参考资料。

优先考虑：

- UNESCO
- Britannica
- 各国国家档案馆
- 国家图书馆
- 大学历史研究机构
- 博物馆
- 历史研究出版物
- 公共数字档案
- 权威历史资料数据库

优先使用免费公开资料。

参考资料应包含：

- 资料名称
- 发布机构
- URL
- 资料类型
- 适用事件
- 必要的备注

禁止：

- 虚构资料来源。
- 编造参考链接。
- 将搜索摘要当作完整史料。
- 将未经核实的观点当作历史事实。
- 为了增加事件数量而降低质量。

如果某条历史事件无法找到可靠来源，应标记为待核实，不要伪装成已经完成史料审查。

## 4.3 历史事件审核

建立数据校验机制。

检查：

- 起止年份是否合理。
- 开始时间是否晚于结束时间。
- 经纬度是否有效。
- 事件类型是否存在。
- ID 是否重复。
- 关联人物是否存在。
- 关联事件是否存在。
- 来源 ID 是否有效。
- 中英文内容是否缺失。
- 人物生卒年份是否与事件年代明显冲突。

对历史事实进行人工可追溯审查。

特别注意不同历史叙述中的争议、定义差异和时间口径。

## 4.4 升级历史关系模型

目前的事件关系不能只依赖 from、to 和一段说明。

设计可扩展的 EventLink 模型。

建议支持：

- direct-cause：直接因果
- indirect-influence：间接影响
- background：背景条件
- related：历史关联
- reaction：回应或反应
- continuation：延续或发展

每条关系应包含：

- 起始事件
- 目标事件
- 关系类型
- 中文解释
- 英文解释
- 证据来源
- 可信度或审核状态

必须严格区分：

时间先后关系 ≠ 因果关系。

例如两个事件发生在前后，并不代表前一个事件必然导致后一个事件。

不要为了让关系网络更加复杂而创造没有依据的因果关系。

## 4.5 历史数据管理工具

根据现有项目架构，建立轻量级数据检查和管理脚本。

要求：

- 不需要后端。
- 不需要数据库服务。
- 不需要付费 API。
- 数据继续以本地静态文件为主要来源。
- 支持自动检查悬空引用。
- 支持数据统计。
- 支持来源完整度检查。
- 支持中英文缺失检查。

可以考虑建立独立的数据校验命令。

例如：

npm run validate:data

具体脚本与 package.json 命令由你根据现有结构决定。

阶段完成标准：

- 数据结构有清晰定义。
- 原有数据兼容。
- 数据校验可以重复执行。
- 历史关系具备类型区分。
- 重要历史事件能够追溯资料来源。
- 不因升级而损坏原有功能。

# 五、第二阶段：World Snapshot
# 世界历史快照系统

优先级：P0

这是本次最重要的产品功能之一。

目前时间轴主要控制事件在地球上的显示。

现在需要将其升级为整个历史世界的时间控制中心。

## 5.1 核心体验

用户选择某个年份时，整个界面都应该同步进入那个历史时刻。

例如：

选择 1850 年。

系统应展示：

- 当年的重要历史事件。
- 欧洲的历史状态。
- 亚洲的历史状态。
- 非洲的历史状态。
- 北美洲的历史状态。
- 南美洲的历史状态。
- 大洋洲的历史状态。
- 各类事件的数量和分布。
- 同时代重要人物。
- 具有代表性的历史关系。

不要简单地把 119 条事件重新排列成一个列表。

需要设计真正有信息层次的历史快照。

## 5.2 世界快照面板

建议采用精致的玻璃拟态界面。

包含：

### 年份概览

- 当前年份。
- 年代名称。
- 活跃事件总数。
- 各类事件统计。
- 重要历史变化。
- 时代背景摘要。

### 大洲概览

按七大洲组织历史内容。

每个大洲展示：

- 事件数量。
- 代表性事件。
- 重要人物。
- 主要历史变化。

点击大洲后：

- 地球镜头飞向对应区域。
- 对应区域事件高亮。
- 快照内容切换到该大洲。
- 用户可以继续点击事件查看详情。

### 事件分类

支持按照：

- 政治
- 战争
- 科技
- 经济
- 思想
- 探索
- 社会

筛选当前年份的历史事件。

### 重要事件排序

支持：

- 重要程度
- 时间顺序
- 地理区域
- 事件类型

## 5.3 同时代历史对比

设计同时代对比体验。

例如用户查看 1850 年，可以同时观察：

- 欧洲工业化发展。
- 清朝晚期的社会与政治环境。
- 美国的领土扩张。
- 非洲殖民扩张的历史背景。
- 日本幕府时期的社会状态。

注意：

这里展示的是有历史依据的内容，不是凭空生成的时代概括。

## 5.4 时间轴升级

保留当前时间轴的核心交互。

增强：

- 年代分段。
- 重要历史节点。
- 事件密度提示。
- 年份快速跳转。
- 拖动过程的实时反馈。
- 自动播放节奏。
- 播放速度控制。
- 当前年代提示。
- 键盘控制。

支持未来扩展至更多历史年代。

不要将数据范围永久写死为 1750—1911。

但也不要为了扩大时间范围而随意补充低质量数据。

## 5.5 历史快照的视觉表现

希望达到：

用户拖动时间轴时，地球上的事件、世界快照、事件统计和相关内容同时变化。

整个过程自然、连续、有沉浸感。

不要每次切换年份都让整个页面重新加载。

# 六、第三阶段：Living Globe
# 动态历史地球升级

优先级：P0

这是 ChronoAtlas 的核心视觉资产。

需要让 3D 地球从一个漂亮的背景，升级成真正的历史探索空间。

## 6.1 事件模式

保留当前六棱柱事件系统。

继续优化：

- 事件出现与消失动画。
- 事件重要程度表现。
- 事件悬停反馈。
- 事件选中反馈。
- 地理位置准确性。
- 事件密集区域的视觉管理。
- 事件文字和提示信息。

避免大量事件同时显示时产生视觉噪声。

## 6.2 历史热区模式

新增历史热区模式。

根据当前年份的历史事件分布，展示全球历史活动的空间密度。

可考虑：

- 事件密集区域的光晕。
- 区域热度。
- 不同事件类型的热区。
- 时间变化时热区动态变化。
- 点击热区后显示事件集合。

注意：

热区表达的是当前数据集中已收录事件的空间分布，不应被误解为真实历史事件发生概率。

## 6.3 历史关系模式

新增关系可视化模式。

支持：

- 直接因果关系。
- 间接影响关系。
- 背景关系。
- 普通历史关联。

不同关系类型使用不同颜色、线型、透明度或动画。

选中事件后：

- 只突出重要关系。
- 支持一跳和多跳切换。
- 展示关系说明。
- 可以点击关系节点。
- 可以从关系继续探索其他事件。

默认不要把所有关系同时显示出来。

## 6.4 历史路线模式

规划可扩展的历史路线系统。

支持：

- 航海路线。
- 探险路线。
- 迁徙路线。
- 战争推进路线。
- 贸易路线。
- 重要历史人物活动轨迹。

路线需要包含时间信息。

用户选择年份时，只显示当时已经发生的路线部分。

路线应当具有方向、运动、起止地点和说明。

路线数据必须有可靠来源。

不要把一条普通弧线伪装成真实历史路线。

## 6.5 镜头与地球交互

继续提升：

- 自由旋转。
- 平滑镜头飞行。
- 区域聚焦。
- 地球缩放。
- 点击事件定位。
- 点击大洲定位。
- 事件之间的镜头过渡。
- 用户手动操作与自动镜头之间的协调。

确保镜头控制不会互相冲突。

用户手动拖动时，应合理中断自动飞行动画。

## 6.6 性能

重点检查：

- Mesh 数量。
- Draw Calls。
- 材质复用。
- 几何体复用。
- Raycaster 性能。
- Bloom 开销。
- Pixel Ratio。
- 移动设备 GPU 负载。

可研究 InstancedMesh、LOD、对象池和按需更新。

但必须先测量再优化。

不要为了追求 InstancedMesh 而进行没有实际收益的重构。

# 七、第四阶段：Causal Web
# 历史因果网络升级

优先级：P1

将当前的历史关联弧线系统升级成真正有解释能力的历史关系网络。

## 7.1 历史关系探索

用户选择一个事件后，系统展示：

- 事件的历史背景。
- 直接前因。
- 直接后果。
- 间接影响。
- 相关历史事件。
- 相关人物。

支持：

- 一跳关系。
- 两跳关系。
- 三跳关系。
- 关系类型过滤。
- 关系说明查看。

## 7.2 历史关系详情

点击关系后，展示：

- 关联的两个事件。
- 关系类型。
- 中文解释。
- 英文解释。
- 历史背景。
- 支持该关系的参考资料。

如果关系尚未经过充分核实，必须明确标记。

## 7.3 历史网络可视化

研究是否适合增加独立的二维关系网络视图。

如果采用：

- 节点代表事件。
- 连线代表关系。
- 节点大小反映重要程度。
- 颜色区分事件类型。
- 关系线区分关联类型。

需要支持拖动、缩放、选中和继续探索。

二维网络视图必须与 3D 地球共享同一套数据和状态。

不要维护两套互相独立的历史关系数据。

## 7.4 历史叙事

选择某个重大事件时，可以提供一条经过整理的历史探索路径。

例如：

工业革命：

蒸汽动力发展 → 工厂生产方式变化 → 铁路发展 → 城市化 → 劳工问题 → 社会思想变化。

这些路径必须建立在已有事件和有依据的历史关系上。

不允许为了叙事效果随意拼接历史。

# 八、第五阶段：Historical People
# 历史人物系统升级

优先级：P1

人物不应该只是事件卡片上的几个标签。

未来人物应当成为独立的历史探索入口。

## 8.1 人物档案

# 九、第六阶段：历史疆域演变
# Historical Geography

优先级：P2，作为 V1.0 后的重要长期方向。

研究动态历史疆域的可行性。

目标是让用户观察：

- 帝国的扩张与衰落。
- 国家边界的变化。
- 殖民地的形成与独立。
- 历史国家的兴衰。
- 重要领土变化。

优先寻找：

- 免费公开历史地图。
- 公共领域历史地图。
- 开放地理数据。
- 具有明确许可的 GeoJSON 数据。
- 可合法使用的历史边界数据集。

考虑与 3D 地球融合。

- 历史边界的时间范围。
- 国家名称与实体映射。
- 历史地理数据精度。
- 争议地区表达。
- 数据授权。
- 不同历史时期的边界定义。

# 十一、第八阶段：视觉模式与探索玩法

在核心功能稳定后，主动研究更多有价值的探索模式。

可以考虑：

### 1. Era Mode — 时代模式

按照历史时期探索：

- 启蒙时代。
- 工业革命。
- 帝国主义时代。
- 革命浪潮。
- 近代民族国家形成。

时代定义必须有可靠历史依据，允许不同学术划分方式。

### 2. Event Journey — 历史事件旅程

用户选择一个事件，系统自动整理一条可交互的探索路径。

用户可以沿着事件、人物和关系继续探索。

### 3. Random Discovery — 随机发现

随机推荐一个具有探索价值的历史事件。

用户可以：

- 发现随机事件。
- 定位到地球。
- 查看事件详情。
- 探索相关事件。
- 进入新的历史路径。

### 4. Historical Compare — 同时代比较

选择两个地区或国家，观察同一时期的历史变化。

比较：

- 政治。
- 科技。
- 经济。
- 社会。
- 战争。
- 文化。

必须确保对比口径合理，避免不恰当的简单排名。

### 5. History Discovery — 历史发现

根据当前浏览事件推荐相关历史内容。

推荐逻辑优先依据：

- 事件关联。
- 同时代。
- 同地区。
- 相同人物。
- 相同事件类别。

不要使用外部 AI 推荐服务。

这些玩法不必全部进入 V1.0，但你需要持续评估其产品价值。

## 18.3 每轮优先级

按照以下顺序评估：

P0：核心功能错误、数据错误、严重体验问题。

P1：能够明显提升产品价值的功能和体验。

P2：性能、架构、可维护性优化。

P3：视觉细节和微交互。

P4：探索性功能和实验性创新。

但如果某项 P3 改动能够带来极高的视觉提升，也可以提前安排。

不要为了完成计划而机械地开发。

## 18.4 避免无效忙碌

不要：

- 为了消耗 Token 而反复重写。
- 为了版本号而制造没有价值的版本。
- 为了炫酷而堆叠大量特效。
- 为了增加代码量而抽象。
- 为了追求功能数量而牺牲质量。
- 重复实现已经存在的功能。
- 不断更换技术栈。

每一轮都必须带来可感知的产品进步，或消除真实存在的问题。

## 18.5 任务暂停条件

只有以下情况可以暂停：

- Token 或执行额度耗尽。
- 工具或运行环境无法继续工作。
- 需要用户提供账号授权或私有资源。
- 需要用户明确承担费用。
- 需要用户处理无法由你合法完成的操作。
- 存在不可逆且有重大风险的操作。

其他情况下自行解决。
